# 个人 OM：草稿直接提交与原生 Git

Git 是 OM 内容、已确认变更理由、来源以及贡献状态的唯一事实来源。

## OM 版本与维护

运行时只使用 `FORGE_PROJECT_DIR` 指定的 OM 仓库。
已有仓库保留其内容和历史；缺失 OM 时创建带初始空提交的 `main`，不自动导入
示例 WD 或知识。已有但尚无提交的仓库也会完成初始提交，只纳入 OM 的三个文档目录。
空 OM 可启动服务，但没有 WD 时不能执行对应 Work，须先由使用者维护 OM。
测试夹具和显式导入仍可在程序内提供初始文档，不属于启动配置或回退路径。

- OM 的版本就是 Git commit，历史版本以「短 commit hash + 提交信息首行」标识；读取和定位版本使用完整 commit hash，不依赖额外的 release 分支。
- 后续 OM 更新、部署和升级不再创建 `releases/*` 备份分支。维护操作需要记录变更前后版本时，记录 commit hash 和提交首行即可，正常提交保留前驱历史。
- `main`、`users/<userId>` 分别承载组织和个人生效版本；`contributions/<contributionId>` 承载选定的组织贡献。
- 这不替代升级前对 OM 仓库、数据库和运行数据的备份，也不授权强推、重写历史或绕过组织贡献审阅。

## 工作台

组织贡献保留按文件选择。比较只列出个人自共同基准发生改动、且当前内容仍不同于组织的文件；组织侧独有更新不会被当作待贡献的个人改动。创建贡献会从 main 创建分支和元数据提交，固定作者、理由和来源。保存选定文件使用原生三方补丁，在隔离索引中保留双方不冲突的改动，通过校验后向贡献分支追加提交。冲突或校验失败不移动贡献分支或生效分支。采纳以非快进合并提交纳入 main；main 变化后拒绝旧候选，需重新创建贡献。文件读取和补丁应用不裁剪首尾空白或改变换行，既有历史不会被自动改写。

贡献只有待处理和已采纳状态，由分支尾提交是否被 main 包含推导，没有数据库中的“已审阅”状态。直接用 Git CLI 合并后，后台和成效基线会显示已采纳；追加新提交后重新显示待处理，必须重新选择和校验。管理员可显式放弃待处理贡献，删除对应分支，不影响 main 或个人分支。保留贡献分支才能继续展示记录，删除已采纳分支会使其不再出现在贡献列表。

每次确认提交都以首行记录摘要，以 `AiricForge-Reason`、`AiricForge-Author`、`AiricForge-Source-Revision` 等 trailer 记录理由、作者及来源。贡献选择提交还记录 `AiricForge-Contribution` 和 `AiricForge-Selected-Paths`，合并提交记录审阅人。HTTP 中 `review` 表示保存选择，`reviewedRevision` 表示当前贡献分支版本。

- **改进工作方式**：可直接开始独立 Reflection，也可从某个 Work 进入。独立讨论不制造 Work 或报告记录。
- 普通问答不自动改 OM。用户明确要求准备改动即可生成私有草稿，不要求先选 Lens 或提供轨迹引用。引用 Work 事件时仍验证来源；可选 Lens 仍限制对应类型的改动。API Suggestion 不修改 OM 或授予工具权限。
- **OM 改动**展示提交前后内容，可以调整、删除文件、丢弃草稿或确认提交。草稿是 `data/worktrees/drafts/<user>/<scope>` 中 detached worktree 的未提交文件，重启后从 Git 差异恢复。保存不会改变生效版本；确认提交校验后创建 commit 并快进个人 OM；确认或丢弃后移除草稿 worktree。未完成讨论的摘要、冲突和同步来源保存在 worktree 私有 Git 元数据中，不存文件内容快照。
- 生效版本变动后必须合并最新版本、解决冲突，再确认提交。浏览器提交带内容摘要和请求 ID，丢失响应后可安全重试。
- **个人 OM**提供手动编辑和组织同步草稿。组织同步同样先查看差异，再直接提交；不会另建 Proposal。
- 既有 Work/Turn 固定的 OM 修订不改写，后续工作使用新的个人版本。个人修改不会自动进入组织 OM。

## 本地 agent 与 Git

1. 打开 **本地 agent 与 Git**，创建访问令牌。密钥只显示一次，服务端只保存摘要；可随时撤销，默认有效期 90 天。
2. 复制页面提供的 clone 地址，使用系统 Git：

   ```sh
   git clone https://forge.example/git/personal/USER_ID.git personal-om
   cd personal-om
   ```

3. 按 Git 提示输入用户名和访问令牌。使用操作系统的安全凭据管理器，不把令牌放进地址、脚本或 OM 文件。
4. 让外部 agent 编辑 OM，检查内容，再执行 `git add`、`git commit` 和 `git push origin main`。成功 push 就是采用，不需要网页再次确认。
5. 服务端已有更新时先 `git pull --rebase`，解决冲突，再 push。不要强推。

令牌绑定所有者，不能访问他人的仓库。客户端只有 `main`，由服务端固定映射到该用户的个人分支；提交作者、URL 和客户端 ref 都不能改变授权。即使是管理员，个人令牌也不能代替别的用户推送。

每次传输使用隔离对象库，不直接提供共享仓库。禁止额外分支、标签、删除、非快进、符号链接、子模块及 OM 目录之外的文件；检查新历史中的每个树，而不只检查最终差异。网页提交和 Git push 都通过相同的个人 OM 校验和发布边界。

仅 OM 文档进入版本库，不应加入报告原件、轨迹、数据库或凭据。路径限制不等于秘密扫描，提交前仍需检查文档内容。

## HTTPS 部署

远程 Git 必须走 HTTPS，只有真正的本机连接可以使用 HTTP。配置：

- `FORGE_PUBLIC_URL=https://forge.example`：公开地址，也用于生成 clone 地址。
- `FORGE_TRUST_PROXY=127.0.0.1`：仅当 TLS 由该受信代理终止时设置。容器部署应填写实际受信代理地址或网段，不要信任任意来源。
- 代理保留 Git 请求路径、认证头、内容类型和响应体，并提供 `X-Forwarded-Proto: https`。后端端口不得直接暴露给非受信网络。

Git 上传最多 16 MiB，每个 OM 文件最多 100,000 UTF-8 字节；还有历史、树大小和传输时长限制。使用维护中的 Git 版本。个人写入锁是单 API 进程内的锁，不支持多个 API 进程同时写同一个工作目录。

## 存储与恢复

Git 是草稿和贡献的唯一内容来源，SQLite 不创建或读取旧 OM 草稿/Proposal/贡献表。当前数据库可重启继续使用，旧产品格式的转换代码已删除。已有运行数据、旧表、Git 历史和引用不会因此自动清理。

备份与跨目录恢复边界见 [恢复契约](contracts/persistence-and-recovery.md)，下一步发布演练见 [集成需求](app-integration.md)。当前行为规格为 [OM Git 场景](acceptance/om-git.feature)。
