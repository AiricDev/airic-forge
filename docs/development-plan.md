# AiricForge 分阶段开发计划

> 状态：实施计划草案；以 `airic-forge-prd.md` 的已确定共识和验收场景为产品基线。  
> 范围：单实例、单业务 App、多用户；先完成个人工作与学习闭环（P0），再完成组织协作与运行增强（P1）。  
> 现状：仓库包含产品与技术设计文档，以及使用本地演示状态的前端原型；尚无 AiricForge 后端实现或端到端验收记录。本文中的阶段完成条件均为未来交付门槛。

## 1. 要实现的行为

业务用户在 App 页面调用 Copilot 完成真实工作。AiricForge 在每轮执行中选定并固定该用户的 Operating Model（OM）版本，按 Work Definition（WD）装配最小必要知识，通过已接受且被 WD 允许的 App 能力操作业务，并保存可查证的轨迹。用户从轨迹发起 Reflection，将可复用经验形成 Subject Knowledge（SK）或 WD 提议，查看差异并亲自采纳；新版本从下一轮生效。API 能力缺口可以形成建议，但不会自动变成工具。组织随后可以有选择地吸收个人改进，成员自行同步。

第一个可交付结果不是一组独立页面或基础设施组件，而是能在模拟业务 App 中重复演示的完整个人闭环：**工作 → 轨迹 → Reflection → 提议 → 作者采纳 → 下一轮行为和版本归因**。

## 2. 现有架构语法与责任边界

| 边界 | 负责的事实与行为 | 不拥有的事实与行为 |
| --- | --- | --- |
| 业务 App | 身份验证、Business State、业务授权、命令事务、回执与结果查询 | AiricForge 的 OM、Reflection 与个人提议 |
| AiricForge 产品内核 | 用户和资源归属、Work/Session/Turn、能力目录接受、OM 版本选择、提议/采纳、规范化轨迹与审计关联 | 绕过 App 修改 Business State；把模型回复当作命令成功 |
| OM 文档与 Git | SK、WD、组织 `main`、个人版本、不可变的已采纳内容及文档来源 | 当前业务记录、密钥、会话状态和未验证的轨迹结论 |
| Context Compiler | 从本轮固定的 OM 修订解析 WD，加载 bootstrap SK，提供有限的 routing surface 和按需读取，并记录文档来源 | 无差别加载整个 OM；让 Agent 自行决定版本或授权 |
| Agent harness | Work 与 Reflection 的对话循环、流式事件和受限工具执行 | OM 采纳决定、业务操作结果、产品级规范轨迹 |
| Web 工作台 / 嵌入式 Copilot | 展示有权访问的资源，收集人类编辑、审阅和采纳决定；App 页面负责命令成功后的刷新 | 通过前端文本或页面状态直接授予业务权限 |

技术设计中的 Node.js、pnpm、pi-sdk 和 ACP 是既定方向；Fastify、SQLite、Drizzle、JSONL 分段、具体包拆分等仍按 proposed 实现选型处理。实施时先固定领域契约，再验证机制是否满足它。`prototype/` 可复用页面信息架构、交互和视觉组件，但其 `DemoContext`、`localStorage`、种子数据及模拟 Reflection 逻辑不是服务端契约。

## 3. 开工前的契约收敛（阶段 0）

这一阶段只解决会改变数据含义、权限或运行结果的分歧；结果应写回 PRD、OM 设计和技术方案，并形成小型契约样例及验收夹具。以下是**建议的收敛方向**，不是声称已经确定的产品事实。

| 决策 | 当前冲突或空白 | 阶段 0 应产出的明确规则 |
| --- | --- | --- |
| OM 文档格式 | `operating-model.md` 以 `definition.md` 和文档 front matter 为例；技术方案与原型使用 `work.yml`、多文件 WD package | 选定一个可校验的首版包格式，明确 WD/SK 的稳定 ID、引用、能力白名单、重命名和迁移规则；保持“元数据供系统解释、正文供 Agent 解释” |
| 个人 active 版本 | PRD 同时出现显式 active 关系和“HEAD 即 active”；技术方案写“commit 即采纳” | 明确哪些提交能改变 active、外部提交如何导入、采纳的并发条件更新，以及 rebase/冲突期间运行时固定到哪个已采纳提交。未采纳编辑不得进入执行上下文 |
| Proposal 与工作区 | PRD 固定每用户一个 worktree、同一时间一个未完成 Proposal；技术方案允许多个 Proposal 分支和临时 worktree | 以产品约束为先，定义工作区占用、外部编辑检测、锁和租约、重启恢复、放弃时保留原有修改的规则；如要改成多 Proposal，先修订 PRD 与验收 |
| Work / Session / Reflection | PRD 的 D09 未决；技术方案倾向每 Work 一 Reflection，且 API Suggestion 没有独立持久对象 | 定义一 Work 对多 Session、Turn 和 Reflection 的基数、恢复键、轨迹选择范围；API 建议作为可跟进产品对象还是仅对话结果，要与 FR-12 一致 |
| 身份与权限 | PRD 验收引用 D01，但待决表未定义 D01；Web 登录仍 Unknown | 明确 Web 与 Copilot 如何复用 App 已验证身份、管理员如何授予/撤销、Email 规范化与最小冲突处理；所有资源接口在服务端做归属校验 |
| App / ACP 契约 | D07、D08、D10 尚未定；App 页面快照、Token 生命周期、能力兼容与未知命令恢复未统一 | 用可执行模拟 App 固定身份、页面文本、ACP 握手/恢复、OpenAPI 能力标识、幂等键、预期版本、回执和按键查结果协议；定义 Token 失效时的动作状态 |
| Reflection lens | PRD 要求三种 lens；原型仅有 Domain Knowledge 和 Delegation Gap | 固定三种内置 lens 的输入、输出、版本归因、无提议结果；明确管理员首版是配置内置 lens 还是可以新增 |
| 运行持久化 | 技术方案把轨迹明细置于 JSONL，把索引置于 SQLite；恢复和跨存储一致性仍待证实 | 定义追加、去重、索引/游标更新、截断恢复和备份一致性规则；保留可读的原始事件与规范化展示，不记录模型私有推理或 Token |

**阶段 0 完成条件：**形成契约决策记录、首版 OM 样例、模拟 App 协议夹具、对象关系与权限矩阵、P0 验收脚本草案。PRD 验收项引用但待决表尚未定义的 D01/D02/D03 要么补齐，要么移除失效引用；不能以技术方案中的 proposed 选择悄悄替代产品决定。

## 4. 分阶段实施

阶段按依赖排序。每阶段都交付可运行的纵向切片；除阶段 0 外，每阶段结束都在浏览器和真实服务中验证。P0 是阶段 1–5 的合并交付门槛，P1 是阶段 6。

| 阶段 | 用户可观察的增量 | 主要责任边界与实现内容 | 完成证据 |
| --- | --- | --- | --- |
| **1. 可部署的身份与 OM 基础** | 空实例启动；两个 App 用户进入工作台，各自看到个人 OM，管理员可查看但不会改变所有者 | **部署/身份边界：**镜像、`/project` 与 `/data` 初始化、App 身份验证、Web/ACP 会话、所有者/管理员鉴权。**OM 边界：**组织 `main`、个人分支及工作区、已采纳修订读取、WD/SK 解析和结构/引用校验。**界面边界：**把原型中的登录、个人 OM 和管理员用户页接入真实 API | 空目录与已有目录启动；同一身份重复进入不重复建号；两普通用户互不可见；管理员读取他人资源不更换其模型所有者；重启后身份和 OM 仍可读。覆盖 P0-01～05、11 的基础部分 |
| **2. App 内完成可追溯的 Work** | 在模拟 App 页面打开 Copilot，启动/恢复 Work，看到流式进度；允许的命令得到 App 回执并刷新页面；AiricForge 工作台可查看同一 Work 的 Turn、Action 和上下文来源 | **App 接入边界：**页面文本、App 专用 OpenAPI 候选/接受、能力标识与 WD 白名单、身份 Token 透传、命令幂等与结果查询。**运行边界：**pi-sdk Work Agent 的受限工具集、ACP、每 Turn 固定 OM 和能力目录版本、Context Compiler 与来源清单。**轨迹边界：**规范事件、回执、未知结果及恢复。**界面边界：**嵌入式 Copilot 与 Work 详情 | 演示被允许的命令、App 拒绝、越权目标、Token 撤销、页面切换、响应丢失后按同一幂等键查结果；每 Turn 能定位 OM 修订、WD/SK 文档与命令回执；断线与重启后可继续读取。覆盖 P0-06～10、18～19 的运行部分 |
| **3. 个人 OM 编辑、提议与采纳** | 普通用户在 Web 中改 WD/SK，查看差异、来源和检查结果，确认一次采纳；下一轮使用新版本 | **文档治理边界：**草稿/外部修改导入、单工作区占用、Proposal 的基准与证据、结构/能力/路径/依赖校验、预期 active 修订的条件提交；修正只产生新提交。**界面边界：**编辑、差异、冲突和历史视图。**运行边界：**每轮重新解析 active，执行中快照保持不变 | 未采纳文件与普通 Git 操作不进入运行时；外部修改不被覆盖；并发采纳只有一个成功且另一请求可恢复；新增 WD 无需重启；旧 Turn 仍能读到原内容。覆盖 P0-12～13、18，并补全 P0-11 |
| **4. 从轨迹到可审核的 Reflection** | 用户从有权读取的 Work 选证据与三种 lens，对话得出有证据的 SK/WD 改动或 API 建议；证据不足时保存分析而不强行产生 Proposal | **学习边界：**Reflection Agent 只读被授权的轨迹证据，只能修改候选 OM 文件，不能调用 App Command API；结果记录 lens 版本、来源事件和归因理由。**治理边界：**工作区占用/并发、防覆盖、Proposal 复用阶段 3 的审阅与采纳。**建议边界：**API Suggestion 可跟进/导出，但不进入工具目录。**界面边界：**Reflection 工作区、提议和建议详情 | 三 lens 都有可演示路径；无证据和仅 API 建议路径不产生空提交；有未完成修改时 Reflection 被阻止且不覆盖；两次同时发起不混写；从 App 工作到下一轮版本变化的浏览器闭环通过。覆盖 P0-15～17、21 |
| **5. P0 交付与恢复验收** | 单镜像和模拟 App 可供新环境部署；故障后用户可找到既有工作与未完成提议 | **部署/数据边界：**迁移、故障恢复、备份还原、凭据隔离、日志与健康检查、最小接入说明。**验收边界：**按 PRD 场景执行真实浏览器、API、Git 和 App 回执验证，记录证据与缺口 | 新环境按说明部署；备份与恢复 `/project`、`/data` 后身份、版本、轨迹、Reflection 和 Proposal 一致；P0-01～13、15～21 逐项有结果与证据；安全/未知命令场景实测通过。P0-14 在 PRD 中缺号，不虚构需求 |
| **6. P1 组织吸收与运行增强** | 管理员比较个人与组织版本，选择性吸收有依据的变更；成员自行同步并处理冲突；可衡量真实改善 | **组织治理边界：**来源与依赖检查、选定内容合并、历史修订保留、组织内容与私人轨迹隔离。**个人同步边界：**rebase/冲突工作流，显式采纳后才改变 active；旧 Turn 引用仍可读取。**产品测量边界：**采纳时长、SK/WD 复用、必要人工决策与可避免纠正分开统计。**运行边界：**明确样本规模后做容量与恢复测试 | P1-01～08 在真实服务通过；组织吸收不暴露私人 Session；成员未同步前版本不变；rebase 不破坏历史归因；形成有样本口径的基线，再制定数值目标 |

**可选后续，不纳入 P0/P1 承诺：**多 App/多租户、跨包 OM 组合、自动 Reflection、自动采纳、完整 Git 托管、历史案例回放式自动采纳门槛、通用组织策略引擎。只有真实使用数据说明需要时再排期。

## 5. 关键依赖与修改闭包

每个纵向切片同时更新拥有该行为的契约、存储、API、界面和验收，避免只完成单层代码。

| 行为变化 | 必须一同修改和验证的边界 |
| --- | --- |
| 新增或改变 WD/SK 格式 | 文档解析与校验、Git 版本读取、Context Compiler、编辑器/差异视图、样例 OM、迁移说明、相关 P0 场景 |
| 改变 active 选择或采纳 | 个人分支/引用、并发条件更新、Turn 快照与轨迹来源、Proposal 界面、重启/冲突测试 |
| 接受或移除 App 能力 | OpenAPI 导入和差异、能力目录历史、WD 白名单、工具注册、现存 Work 兼容规则、命令恢复测试 |
| 改变身份或资源关系 | App 身份验证、Web/ACP 鉴权、所有资源查询/写入、管理员视图、越权回归场景 |
| 新增 Reflection 输出 | Lens 输入与版本、证据权限、结果持久化、提议或 API 建议状态、编辑/审核页面、无提议场景 |

每一步的验收优先证明**行为契约**：实际版本、实际回执、实际 Git 提交和可恢复的轨迹。接口、类型和单元测试用于提前发现错误，但不能替代端到端证据。原型页面应逐页接入真实 API；不把 `localStorage` 演示状态带入生产数据路径。

## 6. 实施节奏与范围控制

1. 以阶段 0 的决策记录建立实现基线。建议先为模拟业务 App 固定一个完整场景（例如原型中的采购流程），同时准备两个权限不同的用户与一名管理员。
2. 阶段 1–4 按端到端切片推进；每阶段都保留可演示版本和未通过的验收清单。阶段 2 的可靠命令与轨迹是阶段 4 学习质量的前提；阶段 3 的真实采纳是阶段 4 形成闭环的前提。
3. 阶段 5 只在 P0 场景实测通过后宣布首版交付。P1 组织协作独立排期，不以尚未定义的组织约束阻塞 P0。
4. 首次真实部署先建立用量、耗时、错误率与人工纠正基线。按相似 Work 比较改进前后，并记录样本、业务必要审批和外部条件；不要把 Proposal 数量当作 Agent 能力提升。

## 7. 计划关闭检查

- 产品闭环覆盖：App 工作、可归因轨迹、人工 Reflection、可审阅提议、作者采纳、下一轮生效、API 建议。
- 权限闭环覆盖：App 业务授权与 AiricForge 资源所有权分开；普通用户隔离；管理员访问不改变模型归属。
- 版本闭环覆盖：未采纳不生效；Turn 内固定；外部提交、并发采纳、冲突及历史读取有明确规则。
- 故障闭环覆盖：未知命令查询、连接恢复、进程重启、工作区恢复、双目录备份和还原。
- 交付证据覆盖：模拟 App、镜像、接入文档、浏览器记录、Git 状态、轨迹与 App 回执。

本计划不以 Airic Framework 旧代码或原型逻辑作为实现完成的证据。迁移旧实现前，逐项核对其责任边界和契约；能复用的模块作为实现候选，不能让历史结构反向决定 AiricForge 的产品规则。
