## **0. Executive Summary**

Airic 企业版是一套可独立部署的 Agent 工作与能力协作系统。首版将与单个业务 App 集成并以内嵌 Copilot 形式提供使用体验，目标是将 Agent 的工作方法与 App 代码解耦，使业务用户在无需编写代码的前提下维护、验证与采纳个人的 Operating Model（OM）；通过可溯源的版本治理与提议流程，支持个人向组织提交贡献并被组织审核吸收，实现经验复用与持续改进。首版闭环包括：标准 App 接入与嵌入式 Copilot、个人 OM 的创作与一次性采纳、组织贡献与同步、基于用户/Work 的版本选择与轨迹可追溯性、人工发起的 Reflection 以及对 App 的 API 能力建议导出。量化基线与目标当前为未知（Unknown），将在首个真实部署后根据观测与可统计事件确定具体数值目标与容量指标。

## **1. 产品定义**

**Airic 企业版是一套独立部署的 Agent 工作与能力协作系统：通过标准契约接入业务 App，作为页面内的 Copilot 协助用户工作；用户用文档维护自己的 Operating Model，基于实际工作持续改进，并通过组织协作共享和吸收经验。**

Airic产品的底层逻辑是：agent trajectory中蕴含的来自实践的知识，随着agent工作的结束被丢弃了，产品设计都是围绕着将agent的行为数据收集起来，挖掘其中的知识，用户就可以自己培养的agent，实现agent能力在部署后的持续进化。

Airic 对外作为一个完整产品交付，包括 Agent 运行服务、Web 工作台、嵌入式交互入口和 Docker 镜像。使用方无需基于 Framework 编写一个新的 Agent 应用。内部可以保留运行时、存储、接入等包边界。

“企业版”目前用于区分产品方向，并不意味着已经确定商业套餐、收费、SaaS 或多租户方案。

Airic 的产品价值围绕一个持续循环形成：

> 在 App 中工作 → 留下可追溯的工作记录 → 人工发起 Reflection  
>               → 提议改进 → 作者确认采纳 → 改善后续工作  
>                             ↓  
>                       贡献给组织  
>                             ↓  
>                       组织审核采纳  
>                             ↓  
>                     其他成员主动吸收  
> ​

## **2. 要解决的问题与目标**

### **2.1 要解决的问题**

* Agent 行为开发与 App 开发耦合，调整工作方法也需要改代码和发布应用。
* Agent 在部署后难以改进，还需要对业务不了解的开发者来设计agent的行为，业务语言的翻译会造成信息失真。
* Agent 的工作过程中能反映出业务流程的真实形态，与真实数据的互动中能产生新的知识，这些资源没有被利用。
* Operating Model 分散在agent代码和prompt中，没有被明确的作为组织资产进行管理。
* 个人实践难以形成组织资产；组织更新又容易覆盖个人已经积累的工作方法。
* Agent 发现能力缺口，流程难以顺利推进时，缺少向 App 团队表达新接口需求的规范渠道。

### **2.2 产品目标**

* 让 App 团队通过稳定的页面、身份和业务能力契约接入 Airic，实现老系统的AI化改造。
* 让业务用户无需了解代码即可维护 Agent 的工作方法和知识。
* 让个人对自己的内容拥有管理权，组织在此基础上管理共享版本与组织约束。
* 让每次模型改进可以追溯到明确的内容差异、判断依据和相关工作证据。
* 让业务操作的权限、约束和最终结果始终由业务 App 决定。

## **3. 已确定的共识**

本节记录本轮产品讨论已经确定的方向。后续章节把这些方向展开为需求；界面文案和具体技术方案另行细化。

编号已确定的决定产品含义

* C01 Airic 作为完整独立应用交付，不再把Airic作为集成进其他APP项目的 Agent framework
* C02 首版一个实例连接一个业务 App支持多用户，不扩展为多 App 平台
* C03 实例挂载的项目仅维护 Operating Model 文档，App 适配遵循标准契约，不在个人项目里编写启动或业务接入代码
* C04 App 提供包含业务逻辑和约束的 API，Airic 学习如何使用能力；新的业务能力仍由 App 团队开发
* C05 App 通过专用 OpenAPI 文档暴露Agent可用的能力
* C06 App 提供与页面对应的文本数据和页面说明，Copilot 能理解当前页面，并通过业务能力API完成操作
* C07 采用同一 Git 仓库、个人分支和组织 `main`个人维护自己的版本，组织吸收个人贡献，个人合入组织更新
* C08 active Operating Model 应与用户/Work 相关；用户agent选择的OM需明确模型所有者与版本快照。
* C09 个人治理简化为查看提议并确认采纳作者可以审核自己的改进，不经过管理员审批，不增加独立激活步骤
* C10 组织管理与个人创作正交组织采纳共享版本，不作为所有个人编辑和采纳的必经关卡
* C11 agent总是选择当前active的版本，OM更新后会在下一轮对话中生效。
* C12 Reflection 首版由人主动发起，基于有权查看的工作轨迹产生模型 patch 或 API 能力建议
* C13 API 建议不自动成为工具，App 发布并经 Airic 接受后，能力才可能被工作定义使用
* C14 Airic以docker image形态发布，运行时的本地目录氛围OM和Runtime两个目录，`/project` 保存git管理的OM模型文档；`/data` 保存账号、Work、轨迹和运行数据
* C15 每个用户有自己的git worktree，外部编辑和普通 Git 提交可导入候选不自动生效，导入不得覆盖外部工作；采纳须防止并发覆盖
* C16 首版采纳检查以结构和能力校验为门槛，不把历史案例回放加入首版采纳流程


## **4. 用户与职责**

Airic 的用户身份以 App 为来源。用户在 App 内打开 Copilot 时，Copilot 使用当前 App 的认证 Token 调用 App 身份接口，获取已验证的当前用户标识；首版暂定使用 Email 作为该标识。

Airic 根据该标识自动完成用户与资源初始化：

* 若 Airic 中不存在对应 Email 的用户，则自动创建 Airic 用户。
* 为该用户创建并关联个人 Git branch 与 worktree。
* 这个身份关联该用户发起的 Work、Session 及其轨迹。
* 同一 Email 后续在 Airic Web 工作台或 App Copilot 中登录时，可查看并管理该 Email 关联且有权访问的资源。

Airic 不将 App Token 本身作为独立的 Airic 用户身份。App 仍负责业务身份的认证、撤销与业务操作授权；Airic 仅基于 App 已验证的用户标识建立自身的用户、资源归属和访问控制。

### **4.1 权限模型**

首版采用简化的资源所有权与管理员权限模型，不引入更细粒度的角色、资源共享层级或逐项权限配置。

| **角色** | **职责** | **Airic 资源权限边界** |
|:---:|-----|--------------|
| 普通用户 | 在 App 中使用 Copilot；创建、维护和采纳个人 OM；查看和使用自己关联的 Work、Session 与轨迹 | 对自己创建或归属的 Session、Work、个人 OM、个人 branch 和 worktree 拥有完全控制权；可查看组织已发布且对成员可见的内容 |
| 管理员 | 初始化和管理 Airic 实例；管理 App 接入、能力目录及组织内容；处理运营与治理事务 | 可访问和管理所有用户的 Airic 数据，包括用户、Session、Work、轨迹、个人 OM、个人 branch 和 worktree，以及组织内容 |
| App 开发团队 | 发布页面上下文和 Agent 可调用的业务 API；评估并实现 API 能力建议 | 不因该职责自动获得 Airic 管理员权限；业务 API 的权限、状态、事务和执行结果始终由 App 控制 |
| 部署运维人员 | 部署、备份、恢复 Airic 服务及管理外部 Git remote | 负责运行环境与数据运维；不因运维职责自动取得 App 业务操作权限 |

### **4.2 资源归属与访问规则**

* Session、Work、轨迹、个人 Operating Model、个人 branch 与 worktree 均关联一个 Airic 用户标识。
* 用户对自己创建或归属的 Session 和 OM 资源拥有完整控制权，包括查看、编辑、创建提议、采纳、运行和删除；具体删除与保留规则待后续设计。
* 管理员可以访问和管理所有用户的 Airic 资源。
* 非管理员用户默认不能访问其他用户的 Session、Work、轨迹、个人 OM、branch 或 worktree。
* 组织内容的维护与个人资源所有权分开判断。组织采纳个人内容以有选择的merge OM的改动到main分支来实现，不自动开放该用户的私人 Session、Work 或轨迹。
* App 业务操作始终由 App 基于当前 App 用户身份重新校验。Airic的Copilot使用App的用户token来调用App的接口，也就是使用当前登录用户的身份。Airic 的资源管理员权限不等同于 App 的业务操作权限。
* 首版不提供除“资源所有者”和“管理员”之外的细粒度 Airic 权限控制。

## **5. 系统边界**

### **5.1 Airic 负责**

* 装配并运行 Agent；维护 Work、轮次、动作和规范化轨迹。
* 维护个人与组织的 Operating Model，提供文档编辑、提议、审核、采纳和历史查看。
* 根据模型所有者和 Work 上下文提供operating model，组装context。
* 管理经过接受的 App 能力目录，并按工作定义与适用规则限制工具可用范围。
* 提供独立 Web 工作台和可嵌入 App 的交互入口。
* 查看agent session，运行 Reflection，管理模型改进和 API 建议。

### **5.2 业务 App 负责**

* 提供与页面对应的，文本形式的页面数据接口，包括页面说明、页面数据和业务对象引用，使 Copilot 获得当前工作上下文。
* 提供selected适合 Agent 调用的Command API，通过OpenAPI文档将接口提供给Airic。
* 使用与网页端同样的access token验证来自agent的api请求。
* 在前端接入 Copilot 面板、页面上下文和操作后的数据刷新。
* 根据 API 能力建议决定是否开发、发布新能力。

### **5.3 双方共同遵守的接入边界**

* 页面文本、用户消息和 Agent 输出只能提供上下文，不能授予权限或成为业务结果的唯一依据。
* Airic使用来自前端的access token，App 仍需检查被代理的业务用户。
* App 与 Airic 可以分别部署和发布，但须遵守已接受的契约版本及兼容性约定。
* 实例配置和凭据保存在运行配置、部署密钥或 `/data`，不进入 Operating Model 文档。

## **6. 核心产品对象**

| 对象  | 定义与用途 |
|-----|-------|
| Operating Model（OM） | Agent 持续使用的工作方法与知识的版本化集合 |
| Work Definition（WD） | 某类工作的入口定义，包括目标、方法、完成条件、知识引用和允许能力 |
| Subject Knowledge（SK） | 可复用的领域知识、术语、经验和判断依据；在产品中称为知识文档 |
| 个人版本 | 个人分支中由所有者采纳、供其 Agent 使用的模型快照 |
| 组织版本 | 组织在 `main` 中采纳并维护的共享模型内容 |
| 组织约束 | 独立于个人内容维护的适用规则；需区分运行时执行的约束与指导性文档 |
| Proposal | 带基准版本、内容差异、来源和理由的改进候选 |
| Adoption | 有权用户确认采纳候选，产生新的当前使用版本的决定 |
| Work | 围绕具体目标持续开展的工作，关联业务目标、参与身份、模型与会话轨迹 |
| Turn | Work 中的一轮执行，固定本轮使用的模型、规则和上下文来源 |
| Action / 命令回执 | Agent 的一次可追溯操作及 App 返回的处理结果 |
| Trajectory | 工作中可观察的消息、上下文、动作、结果与错误记录；不等同于模型私有推理过程 |
| Reflection | 对选定工作证据的分析，可提出模型修改或业务能力需求 |
| API 能力建议 | 给 App 团队的接口设计建议，尚不是可调用能力 |

“Agent 定义”的主要产品入口由 Work Definition 与其引用的知识承担。模型供应商、运行配置和部署凭据由 Airic 服务管理。


## **7. 功能需求**

### **FR-01 独立服务与初始化**

* Airic 以 Docker Image 交付，提供 Web 工作台、Agent 运行服务和嵌入式 Copilot 接口。
* `/project` 保存 Git 管理的 OM 文档；`/data` 保存用户、资源归属、Work、Session、轨迹、提议、采纳记录及运行数据。
* 空 `/project` 可由 Airic 初始化为 Git 项目；已有项目内容不得被启动流程覆盖。
* Airic 管理员可完成实例初始化，并管理 App 接入、能力目录和组织内容。
* 重启后可恢复用户与资源关联、个人及组织版本、Work、Session、轨迹和提议状态。
* Git remote 的推送、拉取、备份与恢复由部署运维人员负责。

### **FR-02 App 能力接入**

* Airic 接受业务 App 专门发布的 OpenAPI 文档，用于描述允许 Agent 调用的 Command API。
* Airic 不默认将整个 App API 暴露给 Agent。
* 能力契约应描述稳定能力标识、命令用途、输入输出 Schema、业务对象约束及版本信息。
* Command API 应支持幂等标识、预期版本、命令回执和结果查询；网络超时或响应丢失时，不得直接认定业务操作失败。
* 导入新版能力目录时，Airic 展示新增、修改、删除及受影响内容；管理员接受前，运行时继续使用已接受目录。
* 能力目录被接受后，Work Definition 仍须显式声明允许使用的能力。
* API 能力建议及未被接受的接口描述不得进入 Agent 可调用工具目录。

### **FR-03 App 身份接入与用户自动创建**

* 用户在 App 内打开 Copilot 时，Copilot 使用当前 App 的 Access Token 调用 App 身份接口，获取已验证的用户标识；首版以 Email 作为 Airic 与 App 的关联标识。
* Airic 使用该已验证 Email 查询用户；若用户不存在，则自动创建 Airic 用户。
* 创建 Airic 用户时，为该用户创建并关联个人 Git branch 和 worktree。
* Airic 将该用户后续发起或归属的 Work、Session、轨迹、个人 OM 和采纳记录关联至该 Email。
* 同一 Email 在 Airic Web 工作台或 App Copilot 中访问时，可查看和管理其有权访问的资源。
* Airic 不将 App Access Token 作为独立 Airic 账号，也不以该 Token 替代 Airic 的资源归属记录。
* Email 更换、多个 App 身份映射同一 Airic 用户及身份冲突处理规则：Unknown。

### **FR-04 资源权限与管理员访问**

* 普通用户对自己创建或归属的 Session、Work、轨迹、个人 OM、个人 branch 和 worktree 拥有完整控制权。
* 普通用户默认不能访问其他用户的 Session、Work、轨迹、个人 OM、branch 或 worktree。
* 管理员可以访问和管理所有用户的 Airic 资源，包括用户、Session、Work、轨迹、个人 OM、个人 branch、worktree 和组织内容。
* 组织内容与个人资源分别管理。组织通过选择性合并 OM 变更至 `main` 吸收个人贡献，但不得自动开放作者的私人 Session、Work 或轨迹。
* 首版不提供资源所有者与管理员之外的细粒度 Airic 权限控制。
* App API 的业务权限、数据访问权限、状态校验、事务处理和操作结果始终由 App 决定；Airic 管理员权限不自动获得 App 业务权限。

### **FR-05 页面上下文与嵌入式 Copilot**

* App 为当前页面提供文本形式的页面说明、页面数据及稳定业务对象引用，使 Copilot 获得当前工作上下文。
* App 前端负责嵌入 Copilot 面板，并向 Airic 传递当前页面、用户选择状态和当前 App Access Token。
* Airic 使用当前 App 用户的 Access Token 调用 App 身份接口和已允许的 Command API。
* 页面文本、用户消息和 Agent 输出只作为上下文，不得单独构成业务授权或业务结果依据。
* 页面切换不得将已发出的业务命令静默转移至其他业务对象。
* App 以自身 API 回执作为命令成功或失败的依据，并在成功后刷新业务页面数据。
* Access Token 失效、撤销或 App 拒绝请求时，Airic 不得继续发起对应业务操作。
* 连接中断后，用户可恢复已有 Work、Session 与轨迹；命令结果未知时，应优先查询原命令的执行结果。

### **FR-06 个人 Operating Model 创作**

* 用户可通过无代码界面创建和维护 Work Definition 与知识文档。
* Work Definition 可声明目标、方法、完成条件、知识引用和允许使用的 App 能力。
* 知识文档可被多个 Work Definition 引用。
* 编辑、保存草稿、外部文件修改和普通 Git 提交均不得自动改变运行时正在使用的 OM 版本。
* 后台编辑、外部文件修改和 Git 提交可导入为包含来源和基准版本的 Proposal。
* 导入过程不得覆盖用户 worktree 中的外部修改。
* 删除、重命名或修改引用关系时，系统应检查文档依赖。
* 新 Work Definition 在被用户采纳后，无需重启服务即可被运行时发现和使用。
* 自动生成的文档候选不得自动获得采纳权限。

### **FR-07 个人提议与采纳**

* 每个 Proposal 应包含修改文件、内容差异、修改理由、来源、基准版本及可用证据。
* 采纳前执行结构校验、能力引用校验、路径安全校验及必要依赖检查。校验不通过时，系统阻止采纳并提供可定位的问题说明。
* 用户查看差异和检查结果后，可一次确认采纳自己的 Proposal，无需管理员审批或独立激活步骤。
* 如果发现来自上游main的改动，提醒用户rebase，用户选择rebase则执行，并手工处理冲突。
* 校验通过只表示满足结构和能力引用要求，不代表工作方法一定正确或效果已经提升，用户自己对修改的质量做判断。
* 已采纳版本与历史记录应保留；修正通过新的 Proposal 和新版本完成，不改写既有执行轨迹。

### **FR-08 组织贡献与版本同步**

* 管理员可以看到各个用户分支与main分支的差异，以及所有的session原始数据，可以在AI的辅助下对个人对OM的改动进行评估和有选择的吸纳。
* 组织贡献应展示原作者、来源版本、内容差异、变更理由和可分享的证据。
* 管理员审核并选择性合并贡献内容至组织 `main`。
* 组织版本由管理员维护；原作者仍管理自己的个人版本。
* 组织约束与个人 OM 演进保持正交。具体可执行规则的发布和作用范围：Unknown。

### **FR-09 用户相关的运行时 OM 与版本归因**

* Airic 每轮运行开始时获取 Operating Model ，依据当前用户和 Work 上下文解析，选择当前用户的active operating model。
* Turn 执行期间产生的新采纳版本仅影响后续 Turn，不得改写当前 Turn 的上下文和轨迹。
* Work、Session 和轨迹应记录模型所有者及实际使用的版本来源。
* 管理员访问其他用户资源时，不得因为管理员身份而静默切换该 Work 的模型所有者。
* 多人参与同一 Work、Work 所有权转移和共享 Session 的模型归属规则：Unknown。

### **FR-10 Work、Session 与轨迹**

* 用户可在 Airic Web 工作台查看自己有权访问的 Work、Session、对话、Turn、动作、命令回执、错误和上下文来源。
* App 中的 Copilot 与 Airic Web 工作台应可定位至同一 Work 和 Session。
* 用户可按 Turn 查看所用 OM 版本、按 Action 查看 App 命令结果、按文档查看上下文来源及版本。
* 管理员可查看所有用户的 Work、Session 与轨迹。
* Reflection 仅可基于发起者有权读取的轨迹证据。

### **FR-11 人工触发的 Reflection**

* 用户可选择有权读取的 Work、Turn 或 Action 轨迹，指定分析问题后主动发起 Reflection。
* Reflection可以选择不同的lens进行不同目的的反思，lens的管理由管理员控制。
* 首版 Reflection 支持三种lens：domain knowledge，delegation gap，与 API Suggestion。
  * Domain knowledge 收集这次work中需要记下的领域知识，存入OM的SK中
  * Delegation gap 回答“那些地方阻碍了agent更加自动的完成这个任务，记住什么规则就可以减少对人的依赖”。
  * API Suggestion 总结工作中是否有API设计不佳导致操作效率低下，容易出错的问题，建议App提供的API作出怎样的改进。
* API Suggestion 这个reflection的结果可能只是给人看的文字，不需要修改OM。所以reflection的结果不完全是OM的修改。
* 没有足够信息是，可以不产出任何proposal

### **FR-12 API 能力建议**

* 用户或 Reflection 可创建 API 能力建议，记录业务场景、现有能力限制、建议操作、输入输出、权限要求及失败语义。
* 针对命令型能力建议，应包含幂等、版本控制和结果查询要求。
* 用户可在 Airic 中查看、跟进 API 能力建议给 App 开发团队；App 团队决定是否实现并发布新能力。
* 新能力只有在 App 发布 OpenAPI 文档、Airic 管理员接受能力目录且相关 Work Definition 明确允许后，才可被 Agent 使用。

### **FR-13 无代码工作台**

* 普通用户的主要入口包括个人 OM（包含变更历史）、Work Session、Reflections（包含Proposal以及是否被采纳）。
* 管理员工作台提供用户与资源查看、组织内容维护、贡献审核、能力目录接受及实例治理入口。
* 工作台应支持 Work Definition 与知识文档编辑、差异查看、Proposal 来源查看、检查结果查看、一次确认采纳和版本历史查看。
* 工作台应支持个人贡献、组织版本浏览、组织更新合入和冲突处理。
* Git branch、worktree、提交和原始 Markdown 作为可展开的高级信息，不作为普通用户完成主要操作的前置条件。
* 具体页面布局、文案、通知、搜索及原型数据属于后续界面设计范围。


## **8. 核心用户流程**

### **8.1 在 App 中启动 Copilot 并开展工作**


 1. 用户在 App 业务页面打开 Copilot。
 2. App 前端向 Airic 传递当前页面、用户选择状态、当前 App Access Token，以及当前的work类型和entity_id。
 3. Airic 使用 Access Token 调用 App 身份接口，获取已验证的用户 Email。
 4. 若该 Email 尚未对应 Airic 用户，Airic 自动创建用户，并创建其个人 Git branch 和 worktree。
 5. Airic 创建或恢复该用户关联的 Work 与 Session，并依据当前用户和 Work 上下文选择用户当前 active Operating Model。
 6. Airic 组装页面上下文与 OM 上下文，开始 Turn。
 7. Agent 仅可调用当前 Work Definition 明确允许、且已被 Airic 接受的 App Command API。
 8. Airic Agent通过ACP协议与Copilot界面通信，同步agent运行状态和进度，每次API命令成功后，App 刷新对应业务页面数据。
 9. Airic 使用当前 App 用户的 Access Token 发起 API 调用。
10. App 基于当前用户身份、目标对象、业务状态和业务规则执行校验，并返回命令回执。
11. Airic 记录 Work、Session、Turn、上下文来源、所用 OM 版本、Action 和命令回执。

### **8.2 用户维护个人 Operating Model**


1. 用户在 Airic Web 工作台打开个人 OM。
2. 用户可以创建或编辑 Work Definition、Subject Knowledge 或其他 OM 文档内容。
3. 因为worktree只能包含一个未合并的proposal，如果存在未提交改动，则不允许启动reflection
4. 当前的HEAD版本为active operating model
5. 若检测到 `main` 存在尚未同步的上游改动，Airic 提醒用户可进行 rebase。
6. 用户选择 rebase 时，Airic 执行 rebase；如存在冲突，用户手工处理冲突后形成更新后的 Proposal。
7. 新版本从后续 Turn 开始生效；已经开始的 Turn 保持原 OM 上下文与版本归因不变。

### **8.3 管理员吸收个人 OM 改进**


1. 管理员在工作台查看各用户个人分支与组织 `main` 的差异。
2. 管理员结合用户的 Session 原始数据、轨迹及相关 Reflection，对个人 OM 改动进行评估。
3. 管理员选择需要吸收的 OM 变更及其必要依赖。
4. Airic 展示原作者、来源版本、内容差异、修改理由及可分享证据。
5. 管理员将选定内容合并至组织 `main`，形成新的组织版本。
6. 组织版本保留作者和来源信息，但不改变作者个人分支的 active Operating Model。
7. 用户在个人 OM 中发现上游 `main` 更新后，可自行选择 rebase 并处理冲突；组织更新不自动覆盖个人内容。

### **8.4 基于轨迹发起 Reflection**


 1. 用户在 Airic Web 工作台选择自己有权访问的 Work Session 轨迹。
 2. 用户选择 Reflection lens，并指定希望分析的问题。
 3. Airic 基于所选轨迹和 lens 生成 Reflection 结果。Reflection的结果将形成对OM的修改Proposal，Proposal体现为用户Worktree未提交的修改，并在Reflection界面总结修改理由、来源和基准版本。
 4. 因为worktree只能包含一个未合并的proposal，如果存在未提交改动，则不允许启动Reflection
 5. Domain Knowledge lens 提取本次工作中可复用的领域知识，并生成写入 Subject Knowledge 的 Proposal。
 6. Delegation Gap lens 分析阻碍 Agent 更自动完成任务的环节，并提出可减少人工依赖的规则或工作方法 Proposal。
 7. API Suggestion lens 分析现有 API 是否存在导致操作效率低或易出错的问题，并生成 API 能力建议。
 8. 用户查看 Proposal 差异与检查结果，可以对变更进行修改，确认后proposal将提交，commit message将包含修改理由、来源和基准版本。
 9. 当证据不足时，Reflection 可以不产生 Proposal。
10. API Suggestion 可以作为仅供人阅读和跟进的结果，不要求修改 OM。

### **8.5 提出并跟进 API 能力建议**


1. 用户或 API Suggestion Reflection 发现当前 App API 无法支持所需工作，或现有 API 设计影响操作效率和正确性。
2. Airic 创建 API 能力建议，记录业务场景、现有能力限制、建议操作、输入输出、权限要求、失败语义，以及命令所需的幂等、版本控制和结果查询机制。
3. 用户或管理员在 Airic 中查看和跟进该建议。
4. App 开发团队决定是否实现该建议，并在实现后通过新版 OpenAPI 文档发布能力。
5. Airic 管理员查看能力目录变更并决定是否接受。
6. 用户在对应 Work Definition 中明确允许该能力，并完成个人采纳后，Agent 才能在后续 Turn 中使用该新能力。

## **9. 数据与版本规则**

| 数据  | 归属与存储原则 | 变化规则 |
|-----|---------|------|
| 模型文档、组织 `main`、个人分支worktree、提交历史 | `/project` 自身的 Git 仓库 | 已采纳内容使用真实提交；候选与治理记录可用独立引用保存 |
| 每人当前使用版本 | Airic 持久化的用户与模型选择关系 | 仅经授权采纳及条件更新改变；具体引用结构待技术设计 |
| Work轨迹、会话与账号 | `/data` | 重启后可恢复；按资源权限访问 |
| 配置和凭据 | `/data` 或部署密钥配置 | 不进入模型文档及对话展示 |
| 业务记录、业务审计、命令回执 | 业务 App  | 由 App 的业务规则和事务保证 |
| 接受的能力契约 | Airic 运行数据 | 保留版本和接受记录，供 Work 绑定和审计 |

工作区中只放模型文档，不意味着整套系统只存文档。Airic 同时维护账号、访问控制、采纳决定、运行状态和学习记录。

备份与恢复需覆盖模型仓库和 Airic 运行数据。业务 App 的数据由 App 自己备份；两端通过工作关联、能力版本与命令回执进行核对。

## **10. 首版范围与暂不包含的能力**

### **10.1 首版必须形成的闭环**

优先级与交付范围（不含具体日期）：

**P0（首要交付 — 首版闭环）**：完成一个端到端的首版闭环，包括单个 App 的标准接入与嵌入式 Copilot；通过已验证的邮箱在 Airic 与 App 侧建立可对齐的身份关联；支持个人 Operating Model 的创作、结构与能力校验，以及作者查看差异后的一次性采纳流程；在 Work 层面实现版本选择与轨迹可追溯；支持人工发起的 Reflection 并产生带证据的 OM patch 或 API 能力建议；提供 Docker 部署与数据持久化与恢复能力。

**P1（次要交付 — 增强与组织协作）**：组织贡献与个人同步功能（含冲突查看与处理工作流）、测量与埋点以便量化迭代效率与复用率、容量与可靠性验证与优化（性能测试、并发规模评估等）。

* 一个 App 的标准接入与嵌入式 Copilot。
* 多用户各自管理文档模型，个人查看差异后一次确认采纳。
* 同库个人分支与组织 `main`，支持贡献、组织采纳、个人合入和冲突处理。
* 按用户解析模型、每轮固定版本、查看工作轨迹与来源。
* 人工 Reflection、模型提议和 API 建议导出。
* 本地账号、职责授权、App 身份验证、Docker 部署和持久化恢复。

### **10.2 首版不包含**

* 多 App 聚合、跨 App Agent 编排、公共模型市场与商业计费。
* 自动运行 Reflection、无人确认的模型采纳。
* Agent 通过修改文档创造新的业务接口，或绕过 App 直接写业务数据库。
* 把历史案例回放作为proposal的自动化验证和采纳门槛。
* 托管 Git remote 推送拉取、完整复刻通用代码托管平台。
* CertReporter 专项接入和旧生成项目迁移。


## **11. 验收要求与交付阶段**

本章将前文产品要求转化为可观察的验收结果。P0 验证个人在实际工作中积累经验、反思并改进 Agent 的闭环；P1 验证组织吸收、成员同步和规模化运行。以下均为目标验收条件，不表示现有实现已经通过。

### **11.1 验收环境与证据**

使用一个模拟业务 App，至少准备两个普通用户和一个 Airic 管理员，并为各身份配置可区分的 App 业务权限。模拟 App 应提供身份接口、页面文本接口、专用 OpenAPI 文档、Command API 和命令结果查询。

验收证据包括界面操作结果、身份与资源关联、Git 分支和 worktree 状态、实际提交、Work/Session/Turn 轨迹及 App 命令回执。不能只以 Agent 回复“已完成”判定通过。

涉及第 13 章尚未统一的规则时，应先明确对应契约，再补齐并执行验收；不得选择一种实现后直接宣布该产品问题已经解决。

### **11.2 P0：个人工作与持续改进闭环**

| 编号  | 验收场景 | 必须观察到的结果 |
|-----|------|----------|
| P0-01 | 使用 Docker 启动空实例并挂载持久化目录 | 可完成实例和 App 接入初始化；用户无需提供 Agent 启动代码；已有项目内容不被覆盖 |
| P0-02 | 新 App 用户首次打开 Copilot | Airic 验证当前 Access Token，从 App 身份接口取得 Email，自动创建用户及其个人 branch、worktree，并关联新建 Work 与 Session |
| P0-03 | 同一用户重复进入或从两个入口访问 | 已验证的同一身份关联到同一个 Airic 用户，不重复创建个人资源；Web 登录的验证方式须按 D01 明确后验证 |
| P0-04 | 伪造 Email、使用失效 Token 或访问他人资源 | 客户端自报 Email 不能代替 App 身份校验；未认证请求被拒绝；普通用户不能读取或操作其他用户的个人资源 |
| P0-05 | 管理员查看和管理用户资源 | 可以访问所有用户的 Airic 资源，包括原始 Session 和轨迹；查看其他用户 Work 不会改变其模型所有者；管理员权限不赋予额外 App 业务权限 |
| P0-06 | 导入新的 Command API 目录 | 可查看差异与影响；接受前不进入工具目录；接受后仍需 WD 明确允许；API 建议本身不可调用 |
| P0-07 | App 页面启动一个业务 Work | 页面说明、文本数据、work 类型、entity_id 与当前用户正确关联；Airic 通过 ACP 向 Copilot 同步运行状态和进度 |
| P0-08 | Agent 调用 Command API | 使用当前 App 用户的 Access Token；App 校验身份、目标、业务状态和规则；成功依据回执确认，页面随后刷新对应数据 |
| P0-09 | 页面切换、Token 撤销或跨业务目标调用 | 已发出的命令保持原目标；撤销后不能继续执行业务操作；App 拒绝越权目标；界面不会将上下文文本当作授权 |
| P0-10 | 命令已执行但响应丢失 | 保持结果未知状态并查询原命令；恢复已有回执，不因重复发起操作产生第二次业务效果 |
| P0-11 | 两个用户维护各自的 OM | 个人 branch、worktree、资源归属和 active 版本相互独立；修改一个用户的 OM 不改变另一个用户的运行版本 |
| P0-12 | 编辑个人文档、保存草稿或导入外部修改 | 候选保留来源和基准；不覆盖 worktree 中已有外部工作；未采纳内容不进入执行上下文；普通 Git 提交的处理按 D02 明确后验证 |
| P0-13 | 用户审核并采纳个人 Proposal | 可查看、修改差异，检查结构、能力引用、路径和依赖；本人一次确认后生成提交，提交说明含修改理由、来源和基准；无需管理员审批或独立激活 |
| P0-15 | worktree 有未提交改动时启动 Reflection | 阻止启动，并说明需先处理当前改动；不能覆盖已有候选；两个同时发起的请求不能在同一 worktree 生成相互混杂的 Proposal |
| P0-16 | 使用三种 Reflection lens | 普通用户可选择 lens，管理员控制 lens 管理；Domain Knowledge 形成 SK 候选，Delegation Gap 形成规则或方法候选，API Suggestion 可只产生人可阅读的能力建议 |
| P0-17 | Reflection 证据不足或只产生 API 建议 | 可以没有 OM Proposal；界面仍保存本次分析结果与来源，不为凑齐结果制造提交；API 建议不改变工具目录 |
| P0-18 | 用户在运行中采纳新 OM，或新增 WD | 当前 Turn 保持原快照，后续 Turn 使用更新后的 active 版本；新 WD 无需重启即可发现；轨迹保留每轮实际版本 |
| P0-19 | 查看 Work、Session 和来源 | App Copilot 与 Airic Web 可定位到同一工作和会话；可按 Turn 查看 OM 版本、按 Action 查看回执、按文档查看上下文来源 |
| P0-20 | 重启或恢复持久化数据 | 用户关联、个人版本、WorkSession轨迹、Reflection、未完成 Proposal 与采纳记录能够恢复 |
| P0-21 | 在浏览器完成个人闭环 | 从 App 开始工作，进入 Airic 查看 Session，选择 lens 反思，修改并采纳 Proposal，再开始下一轮；另可查看并导出 API 建议 |

### **11.3 P1：组织协作与运行增强**

| 编号  | 验收场景 | 必须观察到的结果 |
|-----|------|----------|
| P1-01 | 管理员发现个人改进 | 可比较用户分支与 `main`，结合原始 Session轨迹和 Reflection 评估；支持 AI 辅助，不要求作者先完成另一套细粒度授权 |
| P1-02 | 管理员吸收个人内容 | 只合入选定 OM 变更及必要依赖，保留作者、来源和理由；不把原始 Session、Token 或业务轨迹放入组织 OM |
| P1-03 | 组织 `main` 更新 | 不自动改写用户个人分支或 active 版本；普通成员能发现可同步的上游更新 |
| P1-04 | 用户选择 rebase 或遇到冲突 | 由用户决定是否同步，何时同步；冲突可查看和手工处理；最终采纳与 HEAD 更新时机按 D03 明确后验证；进行中的 Turn 不使用冲突中间状态 |
| P1-05 | rebase 后查看历史工作 | 既有 Turn 仍可定位当时的 OM 内容和来源；重写分支提交不会让原执行证据失去可读取的版本 |
| P1-06 | 组织吸收内容后的普通用户访问 | 普通用户可查看已发布组织内容，但不能因此读取作者的私人 Work、Session 和轨迹；管理员仍按其全局权限访问 |
| P1-07 | 接入测量与反馈 | 可按第 12 章口径统计个人迭代、组织吸收和工作效果，区分模型产出数量与实际改善 |
| P1-08 | 执行容量与可靠性验证 | 在明确的数据量、并发数和故障条件下形成结果，找出瓶颈并验证恢复行为；目标数值另行设定 |

组织约束的具体执行规则尚为 Unknown，不以一套未定义的强制规则引擎作为当前验收前提。规则范围确定后补充相应验收。

### **11.4 交付判定**

P0 交付应包含可运行镜像、模拟 App、App 接入说明、持久化与恢复说明，以及上述关键浏览器流程和故障场景的验证记录。与 P0 相关的待定契约必须先落实，才能关闭相应验收项。

P1 在个人闭环之上交付组织差异审阅、选择性吸收、rebase 与冲突处理，以及量化和容量验证。P1 能力列入整体产品范围，但不与 P0 的最小闭环混为同一交付门槛。

## **12. 成效衡量**

Airic Forge 要验证的是：实际工作产生的经验能否沉淀为可复用知识，并使 Agent 在部署后更可靠、更少需要用户补充工作方法。提交数量、反思次数和生成文档的长度只能描述活动量，不能独立证明能力提升。

### **12.1 衡量维度与口径**

| 维度  | 观察内容 | 口径与解释 |
|-----|------|-------|
| App 接入成本 | 从开始适配到完成一次真实 Copilot 工作所需的开发投入 | 分别记录页面文本接口、身份、Command API 和前端嵌入投入；检查是否仍需为实例编写专属 Agent 代码 |
| 实践经验沉淀 | 有证据的 Reflection 结果、产生的 SK/WD 候选及采纳情况 | 按 lens 区分统计；API Suggestion 和无 Proposal 的有效分析单独记录，不作为失败 |
| 个人迭代效率 | 从发现问题、发起反思到采纳改进的耗时 | 区分分析运行时间、用户审核时间和 worktree 被未完成候选占用的时间 |
| 用户自主维护 | 普通用户独立完成编辑、检查与采纳的情况 | 记录需要管理员或开发者协助的环节，用于判断无代码流程是否真正可用 |
| Delegation Gap 改善 | 相似工作中的补充说明、方法纠正和重复求助是否减少 | 必须由业务规则要求的确认或审批单独统计，不以绕过必要人工环节为提升 |
| 领域知识复用 | 从轨迹沉淀的 SK 是否在后续相关工作中被使用 | 结合实际引用、任务结果和用户反馈判断；被读取不等于有帮助 |
| 工作正确性 | 重复错误、错误重试、用户纠正、业务拒绝与返工的变化 | 同时观察完成结果，避免用更少交互掩盖错误或未完成工作 |
| 组织吸收与扩散 | 被吸收的个人改进、成员同步情况、冲突处理成本 | 在 P1 开始统计，保留个人来源与组织版本对应关系 |
| API 改进闭环 | API 建议被 App 团队采纳、发布及实际使用的情况 | 建议导出、App 发布、目录接受、WD 允许和后续使用分别记录 |
| 可靠性与归因 | Turn 来源完整性、未知命令恢复、重复效果、恢复失败 | 用可验证事件和 App 回执核对，不能从 Agent 文本推测成功 |

### **12.2 测量阶段**

P0 保留支持追溯的基础事件和版本关联，包括身份验证后的用户归属、Work/Session/Turn、所用 OM、Reflection lens、候选基准、采纳提交、Action 与回执。事件中不记录原始 Access Token。

P1 在这些记录之上补充统计口径、反馈入口和比较视图。对改进效果的比较应尽量选择相同工作类型、相近任务难度和可比的业务能力版本，同时记录模型服务变化等影响因素。

这类后续效果观察不等于将历史回放加入自动采纳门槛。是否采纳仍由用户基于差异、证据和结构检查作出判断。

### **12.3 基线与目标**

以下数值目前为 **Unknown**：用户规模、并发 Turn 数、轨迹数据量、响应时间、恢复时间、保留周期、个人迭代耗时目标以及工作效果改善幅度。

首个真实部署应先建立基线，再确定目标和测量周期。对外报告须说明数据范围、样本数量和比较条件，不能把少数成功案例概括为普遍效果。
